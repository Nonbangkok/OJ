# Problem Authoring Slice 1: Data Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a non-destructive PostgreSQL migration mechanism and the complete database/type foundation for Problem Authoring drafts without adding authoring APIs, UI, runner jobs, or publish behavior.

**Architecture:** TypeScript migration modules run in a deterministic registry under a PostgreSQL advisory lock, recording applied IDs in `schema_migrations` and wrapping each migration in its own transaction. The first migration creates the five authoring tables and indexes approved in the design; focused TypeScript row types mirror that schema. Production startup runs compiled migrations before starting Express, while development exposes an explicit migration command.

**Tech Stack:** Node.js 20, TypeScript 5.9, PostgreSQL 16, `pg` 8, Jest 30, ts-jest, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-09-12-problem-authoring-workspace-design.md`

## Global Constraints

- This slice implements only the non-destructive migration mechanism and authoring data models from implementation slice 1 of the spec.
- Existing tables, `backend/scripts/init_db.ts`, existing upload flows, and contestant judging behavior must remain unchanged.
- Migration upgrades must never call the destructive database initialization script.
- UUID values are generated by the application; the migration must not require a PostgreSQL UUID extension.
- Authoring lifecycle values are exactly `draft`, `generated`, `ready`, and `published`.
- Authoring job values are exactly `queued`, `compiling`, `running`, `succeeded`, `failed`, `timed_out`, `cancelled`, and `stale`.
- C++ source and binary authoring fields remain private database fields; no public API is added in this slice.
- Use existing Jest/ts-jest conventions and run the full backend test suite before completion.
- Each task is reviewed and committed independently before the next task begins.

- [ ] **Step 4: Implement the migration service minimally**

Create `backend/services/schemaMigrationService.ts`:

```ts
import { MIGRATIONS } from '../migrations';
import { Migration, MigrationPool } from '../migrations/types';

export const SCHEMA_MIGRATION_LOCK_ID = 734001;

export async function runSchemaMigrations(
  pool: MigrationPool,
  migrations: readonly Migration[] = MIGRATIONS,
): Promise<string[]> {
  const client = await pool.connect();
  let locked = false;
  const appliedNow: string[] = [];

  try {
    await client.query('SELECT pg_advisory_lock($1)', [SCHEMA_MIGRATION_LOCK_ID]);
    locked = true;
    await client.query(`
      CREATE TABLE IF NOT EXISTS schema_migrations (
        id VARCHAR(255) PRIMARY KEY,
        applied_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
      )
    `);
    const appliedResult = await client.query<{ id: string }>(
      'SELECT id FROM schema_migrations ORDER BY id',
    );
    const applied = new Set(appliedResult.rows.map((row) => row.id));

    for (const migration of migrations) {
      if (applied.has(migration.id)) continue;
      await client.query('BEGIN');
      try {
        await migration.up(client);
        await client.query('INSERT INTO schema_migrations (id) VALUES ($1)', [migration.id]);
        await client.query('COMMIT');
        appliedNow.push(migration.id);
      } catch (error) {
        await client.query('ROLLBACK');
        throw error;
      }
    }

    return appliedNow;
  } finally {
    if (locked) {
      await client.query('SELECT pg_advisory_unlock($1)', [SCHEMA_MIGRATION_LOCK_ID]);
    }
    client.release();
  }
}
```

export async function migrateAndClose(): Promise<string[]> {

  } finally {
