# Header-problem harness — build report

Branch `header-problem-content`, worktree
`.claude/worktrees/header-problems`. All new files are under
`content/header-problems/`. Nothing outside that directory was changed, and
the running `oj` compose project was never touched.

## What was built

| path | what it is |
|---|---|
| `Dockerfile` | throwaway build image `oj-content-build` |
| `run.sh` | the only entry point; builds the image and runs the scripts inside it |
| `build.py` | one problem (or all) → `dist/<id>/` in the import layout + `dist/header-problems.zip` |
| `verify.py` | CATALOGUE.md's verification contract, enforced on `dist/` |
| `harness.py` | shared rules both scripts must agree on (mirrors of the backend's) |
| `mdrender.py` | the small Markdown → HTML subset for statements |
| `lib/{pair,vector,stack,queue,priority_queue}.h` | the five `CP::` class templates |
| `statement/rules.md` | the shared ข้อบังคับ partial — one copy, not 50 |
| `statement/style.css` | print stylesheet with the Thai font stack |
| `problems/hp_que09_reverse/` | the pilot problem (8 files) |
| `README.md` | build / verify / import, and how to add problem 51 |

`dist/` and `__pycache__/` are git-ignored.

## Commands

```bash
cd content/header-problems

./run.sh build  --all                          # or: ./run.sh build hp_que09_reverse
./run.sh verify --all                          # exit 0 only if every check passed
./run.sh verify hp_que09_reverse --measure     # also measures how far over the limit slow.h is

OJ_CONTENT_REBUILD=1 ./run.sh build --all      # force a fresh image
./run.sh shell                                 # poke around inside the image
```

Import: upload `dist/header-problems.zip` through **Admin → Problems → Batch
upload**. Problems arrive hidden (`is_visible = false`); publish after a look.
Re-importing an existing id updates only categories/difficulty/collection —
grader files, starter files, testcases and the PDF are left alone
(`batchUploadService.processProblemDirectory`), so correcting a published
problem means replacing its files from the admin page, or delete + re-import.

### TLE evidence

The naive `slow.h` (a correct but **physical** O(n) reverse) was run through a
replay of the judge — cases in order, stop at the first failure:

- case 5, the last case of the 50% subtask: **14 ms** of 1000 ms (comfortable
  headroom, so the easy subtask really is passable without the O(1) trick);
- case 6, the first case of the 50% complexity subtask: **Time Limit Exceeded**,
  `timeout -k 2s 1.0s` exited 124 after 1003 ms;
- case 10 measured with a 15x timeout: **12807 ms, 12.8x the limit**;
- resulting prefix score: **exactly 50%**, which is what the statement promises.

Measured separately in the image, outside the harness, on the same bundle:
slow.h needs 9.96 s on case 6 and 11.9 s on case 7 (raw, untimed-out), versus
13 ms for the reference.

### Thai-text-survives check

Not eyeballed. `build.py` and `verify.py` both run `pdftotext -enc UTF-8` on
the finished `<id>.pdf` and assert that `meta.json`'s `pdf_probe`
(`กลับลำดับของสมาชิกทั้งคิว`) and all six required section headings are present
in the extracted text, that at least 200 Thai base characters came back, and
that at least 50 Thai vowel/tone marks reached the text layer. The build fails
hard if any of that is missing.

**One documented tolerance.** `pdftotext` reproduces Thai *base* characters
faithfully but is lossy about the marks stacked on them: the TLWG fonts carry
the lowered/shifted mark variants as private-use glyphs (`ข้อ` comes back as
`ข` + U+F70B + `อ`), SARA AM decomposes, and some marks are reordered past the
following consonant (`ทั้ง` → `ทัง้`). That is an *extractor* limitation, not a
rendering fault. So the probe comparison strips whitespace and both the
canonical (U+0E31, U+0E34–U+0E3A, U+0E47–U+0E4E) and private-use
(U+F700–U+F71A) marks from both sides, and the "≥ 50 marks" assertion covers
the case the stripping would otherwise hide — a font with no mark glyphs at
all. The rendering itself was additionally confirmed once by rasterising page
1 (`pdftoppm -r 400`) and reading it: `ข้อบังคับ`, `กลับลำดับของสมาชิกทั้งคิว`,
`คงที่` and the rest all draw with correct marks.

### Grader discrimination (ad-hoc, not part of the harness)

Run on the built bundle to confirm the secret grader is not a rubber stamp:

```
empty-template (shipped student.h)       ->   0%  (WA on case 1)
half-done (push/pop ignore aux)          ->  10%  (WA on case 2)
reference solution.h                     -> 100%  (Accepted)
```

The middle row is the design's whole point: a `student.h` that implements
`reverse()` correctly but leaves the pre-existing `push`/`pop` ignoring `aux`
is caught by case 2, because the grader interleaves the new function with the
old ones instead of calling it once at the end.

## Decisions a later author of the other 49 must follow

1. **One mechanism for the class body.** `meta.json`'s `declarations` are
   injected into `lib/<topic>.h` at the single `// @@DECLARATIONS@@` marker,
   and the resulting `<ds>.h` ships to *both* `grader/` and `starter/`. An
   entry may be a bare prototype (the member moves into `student.h`) or a full
   inline definition (the member stays pre-implemented in the header) — that is
   what lets one template serve problems like `hp_stk01_top`, where push/pop
   stay in the header, and `hp_que09_reverse`, where five members move out.
   Never fork a topic template per problem.

2. **Subtask percentages the judge can actually produce.** Scoring is
   stop-on-first-failure with prefix score `round(passed/10 × 100)`, so a
   subtask's cumulative percentage must equal `round(cases_so_far/10 × 100)` —
   i.e. boundaries only at multiples of 10%. `harness.load_meta` refuses
   anything else. Order cases smallest-first.

3. **A complexity subtask must bite at its FIRST case.** `verify.py` requires
   `slow.h` to score exactly the cumulative percentage of the subtasks *before*
   the last one. If `slow.h` survives the first case of the TLE subtask, the
   statement's number is a lie, and verify fails. Size every case of that
   subtask, not just the last.

4. **Outputs are never hand-written**, and `gen.py` must be deterministic
   (fixed seeds). `build.py` re-derives the outputs by running the reference,
   and `verify.py` requires the stored bytes to be byte-identical to what the
   reference produces now — a drifting generator fails rather than silently
   invalidating the bundle.

5. **The statement's sample IS the fixture.** The `ตัวอย่าง` section must hold
   exactly one ` ```sample-input ` and one ` ```sample-output ` fenced block;
   `verify.py` runs the starter against them. A wrong sample fails the build
   instead of misleading students.

6. **Six sections, and the shared partial.** `statement.md` must carry
   `## คำอธิบาย`, `## ข้อบังคับ` (via `{{> rules}}`), `## คำอธิบายฟังก์ชัน main`,
   `## ตัวอย่าง`, `## การทดสอบใน grader` and `{{subtasks}}` (which generates
   `## ชุดข้อมูลทดสอบ`). Never paste the ข้อบังคับ text into a problem; edit
   `statement/rules.md` to change it for all 50.

7. **`pdf_probe` is required** in `meta.json`: a distinctive Thai phrase (≥ 8
   characters) that appears in that problem's own statement. It is what makes
   the Thai check problem-specific rather than a check on the boilerplate.

8. **Testcase budget: ~5 MB per problem, 6 MB hard warning.** 50 problems share
   the importer's 500 MB uncompressed-archive cap (`ARCHIVE_LIMITS`). The cheap
   way to buy complexity separation is *operations*, not data: in the pilot a
   `reverse` command is 2 bytes of input and 0 bytes of output but costs an
   O(n) solution n/2 element moves. Prefer a reverse/query-dominated command
   stream over a bigger array.

9. **Calibrate against the image, not your laptop.** `build.py` warns when the
   reference uses more than 50% of the time limit. The pilot sits at ~1.3% (13
   ms of 1000 ms) with a 12.8x margin on the slow side; aim for a similar gap,
   because the production judge is a different machine and the harness cannot
   measure it.

10. **Grader file rules** (enforced at build time so a bad bundle never
    uploads): flat names matching `^[A-Za-z0-9_][A-Za-z0-9_.-]{0,99}$`,
    extensions `.cpp`/`.h`/`.hpp`, at least one `.cpp`, at most 20 files, 1 MiB
    each, and never a file named like `submission_filename`.

## Deviations and unresolved items

1. **The build image is `ubuntu:24.04`, not Debian trixie like the judge.**
   The brief asked for debian-slim + `wkhtmltopdf`; that combination does not
   exist, because Debian removed `wkhtmltopdf` and trixie has no candidate for
   it. Ubuntu 24.04 is the base `backend/authoring/Dockerfile` already uses for
   exactly this reason, with the same pin (`wkhtmltopdf=0.12.6-2build2`). To
   keep the part that actually affects verification, the image installs
   `g++-14` explicitly and asserts `g++ -dumpversion` is 14 at image build
   time: **14.2.0, the same version the judge image's Debian trixie provides**.
   Everything else (libc, kernel, CPU) still differs, which is why time limits
   carry a wide margin rather than a tight calibration.

2. **The Thai check is mark-insensitive**, for the extractor reasons set out
   above. It is not loosened silently: the normalization is a documented
   function (`harness.thai_comparison_key`), and the "≥ 50 Thai marks reached
   the text layer" assertion closes the hole it would otherwise open.

3. **`harness.py` and `mdrender.py` are extra files** beyond the five the brief
   named. They exist so that "how the build produced the outputs" and "how the
   verifier checks them" cannot drift apart — the compile flags, TLE rule and
   output comparison have exactly one implementation.

4. **The harness mirrors backend constants by copy**, not by import (it is
   Python, the backend is TypeScript): `CPP_COMPILE_FLAGS`, the `timeout -k 2s`
   invocation, `normalizeOutput`, `PROBLEM_CATEGORIES`, the difficulty scale
   and the filename rules. `harness.py`'s module docstring names the backend
   file behind each one. If any of those change in the backend, this file has
   to follow — there is no automated link.

5. **Not exercised end to end against a live OJ.** The bundle was validated
   against `batchUploadService.ts` and `problemZipConfig.ts` by reading them
   (directory layout, `config.json` keys and their validation, `grader/` and
   `starter/` handling, testcase pairing) and by replicating the judge's
   compile/run/compare locally, but `dist/header-problems.zip` has not been
   uploaded to a running instance. That is the one remaining confirmation.

6. **The other 49 problems are not written.** Only the pilot exists. The
   harness is the deliverable; adding a problem should be "create a directory,
   run build + verify".

7. **`author` is `"OJ Header Problem Set"`** in the pilot's `meta.json` — a
   placeholder. Decide the real attribution before importing the set.
