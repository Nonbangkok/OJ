# Topic D — `CP::queue<T>` — nine new problems

Authored: `hp_que01_at`, `hp_que02_back`, `hp_que03_push_front`,
`hp_que04_pop_back`, `hp_que05_m2b`, `hp_que06_m2f`, `hp_que07_erase`,
`hp_que08_rotate`, `hp_que10_merge`. `hp_que09_reverse` (the pilot) was not
touched; neither was the harness, `lib/`, `statement/` or any other topic.

All nine pass `./run.sh build <id>` and `./run.sh verify <id> --measure`
(9/9 in the final combined run). Eight files per problem, nothing else.

## Shared design

Every grader is a sibling of the pilot's: a command stream of several blocks,
each block starting from an empty queue, each naming its own `T` so that
`int`, `std::string` and `long long` are all instantiated per case. All of
them interleave the target with `push` / `pop` / `front` / `back` / `size`,
run a `copy` check (copy constructor + copy assignment, original must be
unchanged) and end every block by draining the queue through `front()` /
`pop()`.

Two additions over the pilot, both aimed at keeping the archive small while
still checking everything:

- **`digest`** folds the whole logical order into one number (read through
  the target function where the target is an accessor, otherwise off a copy),
  so a single misplaced element is caught on a 60,000-element queue for one
  line of output. It is the only non-O(1) command, so every generator caps it
  (10–12 per block) and the reference's own cost stays measured.
- **The block epilogue** prints the elements one by one only up to 200 of
  them, and the digest always. Large cases therefore have ~30 KB of output
  instead of megabytes.

The digest fold is hand-rolled (FNV-style, all-unsigned so UBSan has nothing
to say); `std::hash` is deliberately avoided because its values are
libstdc++-implementation-defined and the expected outputs are produced by the
build image while the judge compiles on its own box.

Every generator carries a **simulation of the ring** (`mCap` / `mSize` /
`mFront`, capacity-1 doubling, `expand()` resetting `mFront`) and then
*asserts* the states the statement promises — wrap-around reads, `mFront == 0`
pushes, `pop_back` past empty, both merge directions, and the element-move
counts that separate the reference from `slow.h`. Several of those assertions
fired during authoring and caught real gaps (a case whose queue never ran
dry, a primer that ate a whole block's command budget, big cases that let the
naive version through).

## Per problem

### `hp_que01_at` — `const T &at(size_t i) const` — difficulty 800
Grader stresses: `at` called through a **const** reference; indices aimed at
slots whose physical position is past the end of `mData` (the generator
computes the first wrapped index and asks for it); `at(0)` / `at(size-1)`
agreement with `front` / `back`; `digest` reads every position through `at`.
Subtasks 4/3/3 → 40/30/30.
Measure: reference **32 ms** of 1000 ms, peak **14 MB** of 256 MB, 4.2 MiB of
testcase data. `slow.h` (walk i slots) scores **70%**: Accepted on 1–7
(case 7: 39 ms), TLE on case 8, and on case 10 it needs **more than 15x** the
limit.

### `hp_que02_back` — `const T &back() const` — difficulty 900
Grader stresses: `back` on a wrapped ring; `back` unchanged while elements
leave the front; the size-1 case where `front() == back()` (every small block
drains down to one element on purpose); `digest` asks for `front`+`back` at
every size from full down to 1.
Subtasks 4/3/3 → 40/30/30.
Measure: reference **52 ms**, peak **14 MB**, 3.9 MiB. `slow.h` (walk to the
last element) scores **70%**: Accepted on 1–7 (case 7: 27 ms), TLE on case 8,
**more than 15x** on case 10.

### `hp_que03_push_front` — `void push_front(const T &)` — difficulty 1000
Grader stresses: `push_front` while `mFront == 0` (the new slot must wrap to
`mCap - 1`, which `mFront - 1` on a `size_t` does not do) and on a ring that
is exactly full (so `ensureCapacity` re-packs and a slot computed before the
call is stale). The generator asserts both states per case.
Subtasks 4/3/3 → 40/30/30.
Measure: reference **51 ms**, peak **14 MB**, 3.7 MiB. `slow.h` (shift the
whole queue right) scores **70%**: Accepted on 1–7 (case 7: 63 ms), TLE on
case 8, **11.7x** on case 10.

### `hp_que04_pop_back` — `void pop_back()` — difficulty 1100
Grader stresses: `pop_back` is called **without** an emptiness check (unlike
`pop`, which the grader skips when empty), and every block is driven to empty
and three calls past it before being refilled and used again — an
implementation without the `mSize == 0` guard turns `mSize` into 2^64-1 and
everything after collapses. The generator asserts the past-empty calls.
Subtasks 4/3/3 → 40/30/30.
Measure: reference **92 ms**, peak **14 MB**, 4.2 MiB. `slow.h` (walk to the
last slot first) scores **70%**: Accepted on 1–7 (case 7: 9 ms), TLE on
case 8 (measured directly: **2.7x** the limit there), **2.9x** on case 10.
This is the thinnest TLE margin of the nine.

### `hp_que05_m2b` — `void move_to_back(size_t i)` — difficulty 1200
Grader stresses: `i = 0` (front element to the back) and `i = size-1` (which
must change nothing), both forced explicitly in every block; moves inside a
wrapped ring, so the run of slides crosses the end of `mData`; bursts of
moves back to back on a queue the previous moves just reshuffled.
Subtasks 4/3/3 → 40/30/30, `has_tle_subtask: false`.
Measure: reference **99 ms**, peak **14 MB**, 1.9 MiB. No complexity subtask:
the reference is O(size − i) and the naive bubble-swap version has the same
order of growth (checked out of band: correct on all 10 cases, slowest case
218 ms), so `verify.py` skips the TLE check. The generator carries a shift
budget (2.5e6 element writes per block) so the expensive front-moves cannot
push the reference towards the limit.

### `hp_que06_m2f` — `void move_to_front(size_t i)` — difficulty 1300
Grader stresses: the mirror image — `i = 0` must change nothing, `i = size-1`
drags the last element all the way forward, the slide direction must run
downwards from `i` (going the other way leaves `i` copies of one value), and
the move-to-front access pattern is exercised as bursts.
Subtasks 4/3/3 → 40/30/30, `has_tle_subtask: false` (same reasoning as #5;
naive version checked out of band, slowest case 216 ms).
Measure: reference **101 ms**, peak **14 MB**, 1.7 MiB.

### `hp_que07_erase` — `void erase(size_t i)`, O(min(i, n−1−i)) — difficulty 1500
Grader stresses: about 45% of the erasures land within 40 positions of the
**front** and 45% within 40 of the **back**, with pushes interleaved so the
queue keeps its length — so a solution that always slides the tail pays the
whole queue length on half the commands, and one that always slides the head
pays it on the other half. The rest are spread over the middle and rationed
by a budget so the reference stays fast. Both edge indices and wrapped-ring
erasures are asserted per case, and each large case is held to at least 1e9
element moves for the naive version (measured TLE threshold on this image is
about 3.2e8).
Subtasks 5/5 → 50/50.
Measure: reference **175 ms**, peak **14 MB**, 5.7 MiB (just inside the 6 MiB
soft budget). `slow.h` (always slide the tail) scores **50%**: Accepted on
1–5 (case 5: 11 ms), TLE on case 6, **4.1x** the limit on case 10.

### `hp_que08_rotate` — `void rotate(size_t k)`, O(min(r, n−r)) — difficulty 1600
Grader stresses: `k` values are *constructed* from the queue's current length,
so three quarters of them reduce to a remainder just below `size()` — a
backward turn of a handful of positions for the intended solution and almost
a full queue walk for a forward-only one. `k = 0`, `k = size()` exactly,
`k = 1`, `k = size()-1` are forced in every block, and some `k` exceed 10^9
(asserted) so a solution that never reduces `k` dies immediately. Rotations
move `mFront` all over the array, so most of them run on a wrapped ring.
Subtasks 5/5 → 50/50.
Measure: reference **129 ms**, peak **14 MB**, 3.8 MiB. `slow.h` (reduces `k`
but always turns forward) scores **50%**: Accepted on 1–5 (case 5: 15 ms),
TLE on case 6, **10.2x** the limit on case 10.

### `hp_que10_merge` — `void merge(queue<T> &other)`, O(n+m) — difficulty 1800
Grader stresses: two queues per block, every command naming the one it acts
on, merges in both directions. The large blocks are **scripted**, because the
interesting states cannot be reached by chance: (1) the source wrapped around
its own array *and* the destination's copy run straddling the end of a
differently-sized array — the case that breaks a merge reusing one modulus;
(2) a small merge into a destination whose own data is wrapped, sized so no
reallocation happens, so the copy lands in the gap before `mFront`; (3) the
big one, 16,000 elements into 32,000; (4) the other direction into a
just-emptied queue, then a merge whose source is empty (must change nothing),
then pushes into the emptied queue. All four shapes are asserted per case.
Subtasks 5/5 → 50/50.
Measure: reference **137 ms**, peak **14 MB**, 3.5 MiB. `slow.h` (regrow to an
exact fit for every element) scores **50%**: Accepted on 1–5 (case 5:
133 ms), TLE on case 6, **8.9x** the limit on case 10.

## Catalogue deviations

1. **`hp_que08_rotate` is not O(1).** The catalogue asks for O(1) per call. In
   this class that is not achievable while `push` stays correct and O(1): the
   logical content is `mData[(mFront + j) % mCap]`, and rotating without
   moving elements would have to read the `mCap - mSize` free slots, which
   hold garbage. A lazy offset in `aux` (the pilot's trick) makes `rotate`
   O(1) but moves the cost into `push`: the free gap is then no longer
   cyclically adjacent to the logical back, so appending needs
   O(min(offset, n−offset)) element moves. The requirement is therefore
   **O(min(r, n−r))** with `r = k mod size()` — O(1) for the common ±1 turns —
   and the TLE subtask separates it from both weaker solutions (no `mod`
   reduction, and forward-only turning). The statement says this explicitly.

2. **`hp_que01`–`hp_que04` have a complexity subtask the catalogue does not
   list.** These were authored with `has_tle_subtask: false` first. Timing the
   naive versions against the finished graders showed they are not merely
   "slower" but far over the limit on the large tier (11.5 s, 5.4 s, 2.1 s,
   2.7 s against a 1 s limit), because the command stream keeps the queue tens
   of thousands of elements long and reads across it. Rather than ship a
   statement that promises speed does not matter while the data says
   otherwise, each of the four now states the O(1) requirement and carries a
   TLE subtask that `verify.py` proves: `slow.h` scores exactly 70%, the
   cumulative percentage of the two subtasks before the last. `hp_que05` and
   `hp_que06` genuinely have no gap (the naive version is the same order of
   growth) and keep `has_tle_subtask: false`.

3. **Difficulty ladder** 800, 900, 1000, 1100, 1200, 1300, 1500, 1600, 1800 —
   climbing, with the pilot's 1500 sitting between `hp_que08` (1600) and
   `hp_que10` (1800). Worth knowing: the ladder follows the catalogue's
   ordering, and intrinsically `hp_que04_pop_back` (a guarded `mSize--`) is no
   harder than `hp_que03_push_front`; its 1100 reflects its position in the
   sequence, not a harder core insight.

4. **`student.h` holds only the target function** in all nine. The pilot moved
   `front`/`back`/`push`/`pop` into the submission file because its lazy
   `reverse` needs them; none of these nine do, so those four stay
   pre-implemented in `queue.h` (injected as complete inline definitions via
   `declarations`) and the graders exercise them as fixed, known-good members.
   Rule 3 of the shared ข้อบังคับ partial (functions marked
   `// You MAY need to edit this function`) therefore does not apply to these
   nine; the statements say which functions are already written and cannot be
   changed.

## Open points

- **Timings come from the build image, not the judge.** The reference uses
  3–18% of the time limit everywhere (32–175 ms of 1000 ms) with ~14 MB of a
  256 MB limit, so it has an order of magnitude of headroom. On the TLE side
  the first failing case is 2.7x–15x over the limit and the last passing case
  for `slow.h` uses 9–133 ms, so the subtask boundaries should survive a judge
  box a couple of times faster or slower. `hp_que04_pop_back` has the
  narrowest margin (2.7x) and is the one to re-check if the judge hardware
  changes.
- **`hp_que07_erase` is 5.7 MiB** of testcase data, the largest of the nine
  and close to the 6 MiB per-problem soft budget. The other eight are
  1.7–4.2 MiB.
- **`author` is the placeholder `"OJ Header Problem Set"`**, matching the
  pilot. Real attribution still needs deciding before the set is imported.
- **Not imported into a live OJ.** Only `build` + `verify --measure` were run.
