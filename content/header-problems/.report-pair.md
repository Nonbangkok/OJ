# Topic A — `CP::pair<T1,T2>` — authoring report

Ten problems, `hp_pair01_equal` … `hp_pair10_ordering`, eight files each and
nothing else. No harness, `lib/`, `statement/` or README file was touched; the
only files added outside `problems/hp_pair*/` are this report.

All ten pass `./run.sh build <id>` and `./run.sh verify <id> --measure`:

```
10/10 problem(s) passed in 18s
```

Difficulty climbs 800 → 1900 in steps of 100 (one 200 step at #9, which is
where the complexity requirement appears).

## Per problem

### 1. `hp_pair01_equal` — difficulty 800

- **Target** `bool operator==(const pair&) const`; `void set(const T1&, const T2&)` is
  moved into `student.h` as an editable pre-existing member. `operator!=` stays
  implemented in the header as `!(*this == other)`.
- **Grader stresses** `pair<int,int>` and `pair<std::string,int>`. Command
  stream interleaves `==` with `set`, copy assignment, copy construction, a
  temporary built from the two-argument constructor, and the
  default-constructed pair. Every printing command prints `==` **and** `!=`
  together, so an `==` that is "always true" or that only looks at one
  component shows up as an impossible digit pair. Each block closes with a
  sweep over the whole array counting equal adjacent elements.
- **Subtasks** 3 cases / 30% (`pair<int,int>`, tiny) · 3 / 30% (adds
  `pair<string,int>`) · 4 / 40% (large, dominated by near-misses that agree in
  one component only).
- **Measured** reference slowest 20 ms of 1000 ms, peak 14 MB of 256 MB;
  2.6 MiB of testcase data. No TLE subtask.

### 2. `hp_pair02_less` — difficulty 900

- **Target** `bool operator<(const pair&) const` (lexicographic);
  `void make_min(const pair&)` is the editable pre-existing member.
  `operator>` stays in the header as `other < *this`.
- **Grader stresses** `pair<int,int>`, `pair<std::string,int>`,
  `pair<int,std::string>`. `first` is drawn from a pool of two or three values
  in the big cases, so most comparisons are ties decided by `second`. `<` and
  `>` are printed together and cross-check each other: an `<` that is true for
  equal pairs prints `1 1`, which no strict order can produce. The closing
  sweep counts ascending and descending adjacent positions over the whole
  array.
- **Subtasks** 2 / 20% · 3 / 30% · 5 / 50% (large, `first` almost always tied).
- **Measured** reference slowest 36 ms of 1000 ms, peak 14 MB; 3.9 MiB.
  No TLE subtask.

### 3. `hp_pair03_gte` — difficulty 1000

- **Target** `bool operator>=(const pair&) const`; `void clamp_low(const pair&)`
  is the editable pre-existing member. The header derives `<` as `!(a >= b)`
  and `<=` as `b >= a`, so both run on the student's `>=` alone.
- **Grader stresses** `pair<int,int>`, `pair<std::string,std::string>`,
  `pair<long long,int>`. Both components come from a pool of 3–5 values, so
  equal pairs are the common case. Two commands exist only to pin the equality
  edge: `self` (an element against itself) and `copy` (a copy-constructed
  element against its original) — both must print `1 0 1` every time. Closing
  sweep reports the `>=`, `<` and `<=` counts over adjacent pairs; the first two
  must add up to the number of positions.
- **Subtasks** 3 / 30% · 2 / 20% · 5 / 50% (large, many exactly-equal pairs).
- **Measured** reference slowest 19 ms of 1000 ms, peak 14 MB; 3.7 MiB.
  No TLE subtask.

### 4. `hp_pair04_swapped` — difficulty 1100

- **Target** `pair<T2,T1> swapped() const`; `void become(const pair<T2,T1>&)` is
  the editable pre-existing member and is itself written with `swapped()`.
  The header adds `round_trip()` = `swapped().swapped()`.
- **Grader stresses** `pair<int,std::string>`, `pair<std::string,long long>`
  (asymmetric: returning `pair<T1,T2>` does not even compile) and
  `pair<int,int>` (symmetric — the one case where a wrong-but-compiling version
  could hide, checked by the same logic). Calls nest: round trip, swap of a
  copy of a swap, and a swap fed into `become`, all of which instantiate
  `swapped()` on the mirrored type too. A `raw` command prints the original
  components afterwards, so a `swapped()` that mutates `*this` is caught. Each
  block closes by hashing the swap of every element.
- **Subtasks** 3 / 30% · 3 / 30% · 4 / 40% (large, nesting-dominated).
- **Measured** reference slowest 25 ms of 1000 ms, peak 15 MB; 4.1 MiB.
  No TLE subtask.

### 5. `hp_pair05_add` — difficulty 1200

- **Target** `pair operator+(const pair&) const`; `pair doubled() const` is the
  editable pre-existing member. The header adds
  `plus_twice(other)` = `*this + other + other`, which adds a pair to the
  *result* of an addition.
- **Grader stresses** `pair<long long,long long>`, `pair<int,std::string>` and
  `pair<std::string,std::string>`. With a string component `+` is
  concatenation and is not commutative, so an implementation that swaps the
  operands passes the numeric blocks and fails here; `chain` prints
  `(A[i]+A[j]) + (A[j]+A[i])` in one expression to make the operand order
  visible. `zero` adds the default-constructed pair (identity for both kinds of
  component). Sums are printed, never stored back, so component values stay
  inside the statement's bounds and nothing can overflow under the judge's
  `-fsanitize=signed-integer-overflow`. The closing sweep hashes the sum of
  every adjacent pair, O(n) in total.
- **Subtasks** 2 / 20% (numeric only) · 4 / 40% (string as `T2`) · 4 / 40%
  (large, both components strings).
- **Measured** reference slowest 44 ms of 1000 ms, peak 16 MB; 4.8 MiB.
  No TLE subtask.

### 6. `hp_pair06_maxpair` — difficulty 1300

- **Target** `const pair& larger(const pair&) const`, ties returning `*this`;
  `larger3(b, c)` = `larger(b).larger(c)` is the editable pre-existing member.
  The header adds `dominates(other)` = `&larger(other) == this`, which only
  works if the reference points at one of the two objects passed in.
- **Grader stresses** `pair<int,int>`, `pair<std::string,int>`,
  `pair<long long,long long>`. Every command prints **which object** the
  returned reference points at — `L`, `R` (or `M` for the middle operand of
  `larger3`), and `X` for anything else — so returning a copy or a reference to
  a local is caught directly rather than hoped for; a correct answer never
  prints `X`. Equal pairs are common, which pins the "ties return `*this`"
  rule via `dom` printing `1 1`. The closing fold finds the array maximum but
  advances the champion **only when the returned reference is the new
  element**, so a copy-returning implementation never advances and prints the
  wrong maximum.
- **Subtasks** 3 / 30% · 3 / 30% · 4 / 40% (large, tie-heavy).
- **Measured** reference slowest 42 ms of 1000 ms, peak 15 MB; 4.8 MiB.
  No TLE subtask.

### 7. `hp_pair07_normalize` — difficulty 1400

- **Target** `void normalize()` (used only where `T1 == T2`); `bool sorted() const`
  is the editable pre-existing member. The header adds `normalize_twice()`.
- **Grader stresses** `pair<int,int>`, `pair<std::string,std::string>`,
  `pair<long long,long long>` — all with `T1 == T2`, as the function requires.
  The `norm` command calls `normalize()` **twice** on the same element and
  prints the pair after each call on one line, so an unconditional swap gets
  the first half right and the second half wrong: idempotence is checked
  directly, not inferred. `from` and `copy` normalise a copy and print the
  original too. Generated inputs are biased towards already-sorted pairs and
  pairs whose components are equal (up to 55% identical in the big cases).
  Closing sweep normalises the whole array, counts `sorted()` (must be all of
  them) and hashes the result.
- **Subtasks** 2 / 20% · 3 / 30% · 5 / 50% (large, already-sorted and
  equal-component pairs dominate).
- **Measured** reference slowest 24 ms of 1000 ms, peak 15 MB; 4.7 MiB.
  No TLE subtask.

### 8. `hp_pair08_by_second` — difficulty 1500

- **Target** `bool less_by_second(const pair&) const`; `greater_by_second` is the
  editable pre-existing member. The header adds `equal_by_second` = "neither
  comes first".
- **Grader stresses** `pair<std::string,int>`, `pair<int,long long>`,
  `pair<std::string,std::string>`. The comparator is **used for real**: a
  hand-written stable bottom-up merge sort, on short windows during the stream
  and on the whole array at the end of every block. It is hand-written rather
  than `std::sort` precisely so an invalid comparator yields a wrong answer
  instead of undefined behaviour inside the standard library. `second` comes
  from a pool of 2–3 values in the big cases and a third of the pairs are exact
  duplicates, so the sorted permutation is decided by the `first` tie-break and
  by strictness on equal pairs; the stable sort makes exactly one order
  correct. Every comparison is printed in both directions, so equal pairs read
  `0 0` and a non-antisymmetric comparator reads `1 1`.
- **Subtasks** 2 / 20% · 3 / 30% · 5 / 50% (large, ties on `second`).
- **Measured** reference slowest 51 ms of 1000 ms, peak 15 MB; 4.0 MiB.
  No TLE subtask.

### 9. `hp_pair09_accumulate` — difficulty 1700 — **has the TLE subtask**

- **Target** `pair& operator+=(const pair&)`, returning `*this`;
  `absorb_twice` is the editable pre-existing member. The header defines
  `operator+` on top of `+=` (a copy, then `+=`), exactly the way the standard
  library pairs the two — which is how it "agrees with #5's `+`" by
  construction.
- **Grader stresses** `pair<int,int>`, `pair<long long,std::string>`,
  `pair<std::string,std::string>`. `chain` evaluates `p += q += r` and `twice`
  evaluates `(p += A[j]) += A[j]`, both of which are only right if `+=` updates
  `*this` *and* hands back a reference to it; `absorb` additionally prints
  whether the returned reference is the object itself. `agree` prints
  `A[i] + A[j]` beside a copy of `A[i]` that was `+= A[j]`; they must match
  character for character. The hot command `acc` prints nothing and folds
  array elements into one of four accumulators; the large cases aim ~99.9% of
  their commands at a single accumulator whose two `std::string` components
  grow to ~880,000 characters each. `show` reports each component's **length
  and hash** rather than the component, so a 900 KB accumulator costs a few
  bytes of expected output. The array itself is read-only, so accumulated
  integers stay under 6·10⁷ and nothing overflows.
- **Complexity separation** the reference appends in place (`first += …`),
  O(L) in total. `slow.h` is correct but builds a new pair and copies it back,
  which copies the whole accumulated string every call — O(q·L), about
  12·q² bytes.
- **Subtasks** 3 / 30% (tiny, mostly numeric) · 3 / 30% (medium, strings
  appear; case 6 is the largest case the naive version still passes) ·
  4 / 40% (40,000–55,000 accumulations into one accumulator).
- **Measured** reference slowest 73 ms of 1000 ms, peak 15 MB; 2.0 MiB of
  testcase data. `slow.h`: 22 ms of 1000 ms on case 6 (the last easy case),
  Time Limit Exceeded on case 7, scores exactly 60%; on case 10 it needs
  **8166 ms, 8.2× the limit**.

### 10. `hp_pair10_ordering` — difficulty 1900

- **Target** all six of `==`, `!=`, `<`, `<=`, `>`, `>=`, mutually consistent;
  `clamp(low, high)` returning a reference is the editable pre-existing member.
  The header adds `compare_sign` (−1/0/+1 from `<` alone).
- **Grader stresses** `pair<int,int>`, `pair<std::string,int>`,
  `pair<long long,long long>`. The `laws` command is the heart of it: over
  **every ordered pair** inside a short window it checks the six consistency
  laws from the statement (`==`/`!=` complementary, `<`/`>=` complementary,
  `>`/`<=` complementary, `<=` = `<` or `==`, `>=` = `>` or `==`, and exactly
  one of `<`, `==`, `>`) and reports how many were violated — which must be
  zero. `self` has exactly one correct answer, `1 0 0 1 0 1`; `sign` prints
  `compare_sign` both ways, which must be exact opposites. `clamp` returns a
  reference and the grader prints which object it points at. Each block closes
  with a law sweep over all adjacent pairs plus a stable merge sort driven by
  `<`, both hashed, so the whole array is covered in O(n) and O(n log n).
  Equal pairs and ties on `first` dominate the big cases, which is where six
  separately written operators stop agreeing.
- **Subtasks** 2 / 20% · 3 / 30% · 5 / 50% (large, equality-heavy).
- **Measured** reference slowest 43 ms of 1000 ms, peak 15 MB; 3.4 MiB.
  No TLE subtask.

## Extra checks run beyond `verify.py`

`verify.py` skips the TLE check whenever `has_tle_subtask` is false, so the nine
`slow.h` files it never compiles were checked by hand, in the build image, with
the judge's own flags: all nine compile and reproduce the stored reference
outputs byte for byte on all 10 cases (slowest 13–55 ms). They are genuinely
correct, only wasteful — not stand-ins.

A mutation pass confirms each secret grader really distinguishes a
plausibly-wrong submission from a right one. One realistic single-line mutation
of each `solution.h`, compiled against that problem's grader and run on all ten
cases:

| problem | mutation | caught on case |
|---|---|---|
| `hp_pair01_equal` | compares only `first` | 3 |
| `hp_pair02_less` | or-of-components comparator | 1 |
| `hp_pair03_gte` | strict on the tie (equal → false) | 2 |
| `hp_pair04_swapped` | returns a default-constructed pair | 1 |
| `hp_pair05_add` | operands commuted | 3 |
| `hp_pair06_maxpair` | ties go to `other`, not `*this` | 2 |
| `hp_pair07_normalize` | unconditional swap (not idempotent) | 1 |
| `hp_pair08_by_second` | no tie-break on `first` | 2 |
| `hp_pair09_accumulate` | forgets the second component | 1 |
| `hp_pair10_ordering` | `<=` loses the equality case | 1 |

Every mutant is caught inside the first subtask, so a wrong submission scores
0–20% rather than most of the marks.

## Catalogue deviations

1. **`has_tle_subtask` is false for nine of the ten.** The catalogue's topic-A
   targets are all O(1) on two components, so there is no honest complexity
   subtask to build: any "slow" version differs from the reference by a
   constant factor. The one exception is #9, where accumulating into a
   `std::string` component makes "rebuild the pair and assign it back" O(q·L)
   against the reference's O(L) — a real, textbook separation, and that is the
   problem that carries the TLE subtask. I did consider and reject a
   complexity angle for #8 (a comparator that builds `swapped()` temporaries):
   making it slow enough needs ~2000-character components, which blows the
   6 MB per-problem testcase budget long before the comparator becomes the
   bottleneck.
2. **Every problem adds pre-existing members beyond the catalogue's target
   column.** The catalogue's topic-A table lists only the target operator, but
   the brief requires the grader to interleave the target with "the class's
   other operations" so that breaking a pre-existing function is caught — and
   `CP::pair` as shipped has nothing but two fields and two constructors. Each
   problem therefore declares (a) one editable pre-existing member that lives
   in `student.h`, is already correct, is marked
   `// You MAY need to edit this function`, and is called by the grader, and
   (b) one or two members that stay *implemented in the header* and are written
   on top of the student's target, so the target is exercised indirectly as
   well. These are listed per problem above.
3. **Grader instantiations differ from the catalogue in two rows.** #3's
   "equal pairs must be `true`" and #6's "returns a reference, not a copy" name
   no types, so I chose three instantiations each (listed above) rather than
   two. #9 and #10 likewise got three. Rows 1, 2, 4, 5, 7, 8 follow the
   catalogue's named types and add one more.
4. **Problem titles and statements are new text**, in Thai, in the course's
   voice, with the six sections the shared partial and `hp_que09_reverse`
   establish. Ids are exactly as the catalogue gives them.

## Open points for the controller

- **Testcase data sits at 2.0–4.8 MiB per problem** (total ≈ 38 MiB for the
  ten), inside the harness's 6 MiB soft budget but not by a wide margin on
  #5/#6/#7. If the 50-problem archive turns out tight, the cheapest reduction
  is the last two cases of each generator's `PLAN`; I already trimmed #1, #3,
  #4, #7 and #8 once for this reason.
- **#9's time limit has the least headroom in relative terms**: the reference
  uses 73 ms of 1000 ms here, which is fine, but most of that is `show`
  streaming the 900 KB accumulator ~14 times. If the production judge is much
  slower at I/O than this image, the `show` frequency in `HOT` (weight 1 in
  ~4013) is the dial to turn down. The TLE side has 8.2× margin, so lowering
  `show` costs nothing.
- `dist/header-problems.zip` is shared with the other topics' agents; I only
  ever built and verified by id, never `--all`.
