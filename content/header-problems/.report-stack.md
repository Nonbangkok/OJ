## The shared grader design

All ten graders read the same shape of COMMAND STREAM — blocks, each with its
own `T` (`int`, `std::string`, `long long`; every case uses at least two) —
and all of them

* interleave the target function with `push` / `pop` / `top` / `size`, so an
  edit that breaks a pre-existing member is caught even when the target
  itself is right;
* exercise the copy constructor and copy assignment, then check that the
  ORIGINAL is unchanged via the end-of-block drain;
* end each block by draining the stack through `top()` / `pop()`, printing
  the first 100 elements and an FNV-1a hash of **every** value the grader
  ever read. The hash is what makes the large cases affordable: a query that
  folds instead of printing is two input bytes and no output at all, which is
  how a case asks for `min()` or `reverse()` a hundred thousand times inside
  the ~6 MB per-problem data budget while staying order-sensitive.

### 1. `hp_stk01_top` — 800
`top()` is one indexed read. Grader stresses: `top()` asked for in the middle
of a changing stack, `top()` must not mutate (it is taken by const reference,
so a non-const implementation does not even compile), three `T`, copies.
Measure: reference slowest **12 ms / 1000 ms**, peak **13 MB / 256 MB**.
`slow.h` (walks the array to find the last live slot) is not run —
`has_tle_subtask: false`.

### 2. `hp_stk02_second` — 900
`mData[mSize - 2]`. Grader prints `top` and `second` next to each other, asks
right after a `pop`, and uses `-` for `size < 2`; the pop-heavy mix keeps the
stack falling to 2, 1 and 0 elements. Measure: **11 ms / 1000 ms**, **13 MB**.

### 3. `hp_stk03_at` — 1000
`k` counts down from the top, `mData` counts up, so the index is mirrored.
Grader over-represents `k = 0` and `k = size - 1`, and a `sweep` command
reads the WHOLE stack through `at(0) … at(size-1)` into the hash (budgeted,
12 per large block), so an `at()` that is only right near the top fails.
Measure: **22 ms / 1000 ms**, **13 MB**.

### 4. `hp_stk04_pop_many` — 1200
The real content is the `size_t` guard: `mSize -= k` with `k > mSize` wraps
to ~2^64. The stream uses `k ∈ {0, 1, size-1, size, size+1, ~10^9}` and the
grader prints the resulting size after every `pop(k)`. Measure:
**13 ms / 1000 ms**, **13 MB**.

### 5. `hp_stk05_swap_top` — 1300
O(1) exchange through a temporary (three `T`, so arithmetic swaps are out),
and "do nothing" below two elements. Grader has a `twice` command (swap twice
→ the top must be the same element) and reads the top TWO elements out of a
copy, which is how it sees both halves of a swap without disturbing the
original. Measure: **14 ms / 1000 ms**, **13 MB**.

### 6. `hp_stk06_deep_push` — 1600
First problem where `top` / `push` / `pop` move into `student.h` as editable.
O(k) shift, `k` clamped to `mSize`. The pointed trap is aliasing: the grader
calls `deep_push(k, top())`, so the value must be copied before
`ensureCapacity` reallocates or the shift overwrites it. Measure:
**77 ms / 1000 ms**, **13 MB**.

### 7. `hp_stk07_mitosis` — 1800
One `ensureCapacity(mSize + k)` and one forward copy. The trap is
`push(mData[base + i])` in a loop, which hands `push` a reference into the
array `push` may reallocate; the generator deliberately fires a `mitosis`
while `mSize == mCap` (size an exact power of two). The stack is held at
≤ 60,000 elements by the simulated-size generator. Measure:
**21 ms / 1000 ms**, **14 MB**.

### 8. `hp_stk08_min` — 2200 — TLE subtask
`aux` holds the INDEX of the minimum (it cannot hold the value: `aux` is an
`int`, `T` can be a string), `push` compares against it in O(1), and only a
`pop` that removes the minimum looks for a new one. Small cases push long
DESCENDING runs and use a `popmin` command (pop, then print `min`), so
"remember the smallest value ever seen" dies there; large cases are
fold-`min` dominated with the minimum parked at the bottom, so the reference
never rescans. Measure: reference **27 ms / 1000 ms**, peak **14 MB / 256 MB**.
`slow.h` (scan inside `min()`): Accepted on cases 1–5 (**39 ms / 1000 ms** on
case 5), **TLE on case 6**, scores exactly 50%; on case 10 it needs
**7783 ms = 7.8× the limit**.

### 9. `hp_stk09_reverse` — 2700 — TLE subtask
`reverse()` flips one bit. The elements live in a window
`mData[lo … lo+mSize-1]` and `aux = 2*lo + flip`, because once the stack is
read backwards a `push` has to prepend. `expand`/`ensureCapacity` are
unusable (they assume the data starts at 0), so `push` grows `mData` itself
and re-centres the window — O(mSize) per re-centre, Ω(mSize) free slots at
both ends afterwards, hence amortized O(1). Grader pushes and pops in both
directions, and rotates/reverses a copy to prove the lazy state survives
copying. Measure: reference **21 ms / 1000 ms**, peak **14 MB / 256 MB**.
`slow.h` (physical O(n) reverse): Accepted 1–5 (**21 ms** on case 5), **TLE on
case 6**, 50%; on case 10 **6344 ms = 6.3×**.

### 10. `hp_stk10_rotate` — 3100 — TLE subtask
`aux = block * 65536 + shift` records a rotation that has NOT been performed:
the top `block` slots are read as a ring. A `rotate` with the same `k` is one
subtraction; `top()` is one modulo; the deferred work is flushed (three
reversals, O(block), no extra memory) by a `rotate` with a different `k`, by
`push` and by `pop`. A run of `m` rotates on a block of `k` costs O(k+m)
instead of O(k·m). The large cases are built as runs: `rotate k` once, then
thousands of two-byte `again` commands, then a short interlude of
push/pop/top (the flush points), then a new `k`. Measure: reference
**161 ms / 1000 ms** (the string case, where flushes copy `std::string`s),
peak **14 MB / 256 MB**. `slow.h` (rotate for real every call): Accepted 1–5
(**11 ms** on case 5), **TLE on case 6**, 50%; on case 10 **7702 ms = 7.7×**.

## Catalogue deviations

1. **`min()` is O(1), but `pop` is allowed O(size) when it removes the
   minimum.** A genuinely O(1) min-stack needs either a second stack or
   value encoding; `CP::stack` offers one `int aux` (which cannot hold a `T`)
   and `expand()` copies only `mData[0 … mSize)`, so no auxiliary layout
   survives a resize. The index-in-`aux` solution is the honest fit: `min()`
   and `push` are O(1), a `pop` of the minimum rescans. The statement says
   this explicitly and the large cases keep that event rare (minimum at the
   bottom), so the data separates "O(1) min" from "scan per query" — which is
   what the catalogue row actually asks for ("an O(n) scan must TLE; `pop`
   must restore the previous minimum").

2. **`rotate(k)`'s bound is stated per RUN, not per call.** Rotating the top
   `k` by one cannot be O(1) per call for arbitrary `k` with an array; it can
   be O(1) per call within a run of equal `k` plus O(k) per flush. The
   statement promises exactly `O(k + m)` for `m` consecutive rotates with the
   same `k`, and the large cases are built as such runs — the catalogue's
   "the amortized bound is the point".

3. **`hp_stk09_reverse` requires `push` to manage `mData` itself.** With the
   data in a window, the class's `expand`/`ensureCapacity` would corrupt it.
   The statement spells out that reallocating `mData` inside `push` is
   expected and does not conflict with ข้อบังคับ (no new members; `mData`,
   `mCap`, `mSize`, `aux` are all existing ones).

4. **Seven of ten have `has_tle_subtask: false`** (problems 1–7), matching
   the catalogue, which only promises complexity subtasks for `min`,
   `reverse` and `rotate`. Their `slow.h` files are still correct-but-naive
   implementations (O(n) `top`, array-rebuilding `swap_top`, per-call
   reallocating `deep_push`/`mitosis`, …) and each file says so in its header
   comment; `verify.py` records the check as "skipped" for them.

5. **`hp_stk10_rotate` caps the stack at 30,000 elements** (stated in the
   bounds) because two numbers must share one `int aux`. The generator
   simulates the size and never exceeds it.

## Unresolved / notes for review

* The `again` command in problem 10's grader exists purely to buy TLE margin
  per archive byte; with a plain `rotate k` stream the naive solution was
  only 2.7× over the limit on the hardest case, which felt too thin for a
  different judge box. It is now 7.7×.
* Reference headroom is ≥ 6× the limit everywhere except problem 10
  (161 ms of 1000 ms, i.e. ~6×) and problem 6 (77 ms). No build emitted the
  harness's ">50% of the time limit" warning.
* `slow.h` headroom on the last easy case is 11–39 ms everywhere, so a
  student's naive solution should score the promised 50% (or 30/70) on a
  slower judge too.
* Problems 1–5 keep `push`/`pop`/`top` as complete inline definitions in
  `stack.h` (nothing to break); problems 6–10 move them into `student.h`
  marked "You MAY need to edit". 9 and 10 say "you WILL need to edit".
