files each and nothing else. The harness, `lib/`, `statement/` and the README

**Status: all 10 pass `./run.sh build <id>` and `./run.sh verify <id> --measure`.**
Final run: `10/10 problem(s) passed in 109s`.

## Shared design

Every grader follows the pilot's shape and adds three devices that the
catalogue's intent needs:

- **An order-sensitive 64-bit digest of the whole vector**, printed at every
  checkpoint and at the end of each block. Printing a million elements would
  blow the 6 MB testcase budget; the digest checks all of them for ~20 bytes.
  All of its arithmetic is unsigned, because the judge compiles with
  `-fsanitize=signed-integer-overflow -fno-sanitize-recover` and a signed
  overflow *in the grader* would abort the run.
- **Work-per-byte commands.** Elements, position lists and value blocks are
  manufactured inside the grader from a seed (`1 n seed`, `2 k seed`,
  `10 count seed …`), so one short line can demand a million operations. That
  is why every problem's data is 25–102 KB rather than megabytes.
- **Three element types per problem** (`int`, `std::string`, `long long`), plus
  copy-constructor / copy-assignment checks, `resize`, `clear`, `operator[]`,
  `size`, `empty` and (where the student cannot affect it) `capacity`
  interleaved with the target function.

`capacity()` is printed only where the header alone decides it. In
`hp_vec05_insert` and `hp_vec07_range_insert` the growth strategy is the
student's own choice, so capacity is deliberately *not* part of the answer —
only `size()`, the element order and the clock.

Reference timings below are from the build image on this machine; the
`--measure` figure for `slow.h` on case 10 reads "more than 15x the limit"
because 15× is the harness's own measurement cap (`MEASURE_TIMEOUT_FACTOR`),
not because the margin is only 15×.

## Per problem

### 1. `hp_vec01_fill` — 800, no TLE subtask

- **Target:** `void fill(const T &value)`.
- **Grader stresses:** `fill` interleaved with `resize` up and down, `clear`,
  single-element writes and the copy operations; `size()`/`capacity()` must be
  untouched; empty-vector fill must be a no-op; the digest covers every
  element, so filling part of the range (or past `mSize`) is caught.
- **Subtasks:** 3 / 3 / 4 cases = 30 / 30 / 40 % — `n ≤ 10`, `n ≤ 2 000`,
  `n ≤ 10⁶`.
- **Measured:** reference slowest 141 ms of 1000 ms, peak 14 MB of 256 MB;
  48.6 KiB of data.

### 2. `hp_vec02_at` — 900, no TLE subtask

- **Target:** `T &at(size_t)` and `const T &at(size_t) const`.
- **Grader stresses:** both overloads (the non-const one is written through,
  which only compiles if it really returns `T&`; the const one is reached
  through a `const` reference, and the whole-vector digest is computed through
  it); indices aimed at four regions — inside, `== size()`, inside the
  *reserved* capacity `[size(), capacity())`, and up to `SIZE_MAX`. The
  reserved region is what catches a check written against `mCap`, and
  `index == size()` catches `>` vs `>=`.
- **Subtasks:** 3 / 3 / 4 = 30 / 30 / 40 % — `n ≤ 10`, `n ≤ 2 000`, `n ≤ 10⁶`.
- **Measured:** reference slowest 137 ms, peak 26 MB of 256 MB; 52.9 KiB.

### 3. `hp_vec03_pop_front` — 1000, no TLE subtask

- **Target:** `void pop_front()`; `push_back` is pre-implemented in the header
  through `meta.json`'s `declarations`.
- **Grader stresses:** bulk `pop_front` counts that *exceed* the current size
  (the empty-vector no-op, tested in bulk — the trap is `mSize--` wrapping
  around on an unsigned zero); `capacity()` printed after every build and
  append, so an implementation that reallocates is visible; copies popped
  while the original must stay intact.
- **Subtasks:** 3 / 3 / 4 = 30 / 30 / 40 % — `n ≤ 10`, `n ≤ 2 000`, and
  `n ≤ 100 000` bounded by *total element moves* (~4 × 10⁷) rather than by a
  call count, because `pop_front` is Θ(n) by design.
- **Measured:** reference slowest 65 ms, peak 13 MB of 256 MB; 30.0 KiB.

### 4. `hp_vec04_erase` — 1100, no TLE subtask

- **Target:** `void erase(size_t pos)`; `push_back` pre-implemented.
- **Grader stresses:** positions aimed at 0, `size()-1`, the middle, exactly
  `size()` and far past the end (all of which must be no-ops, *not* "erase the
  last element"); `10 k pos` erases k times at the same position, walking from
  inside the vector to past its end inside one command; capacity printed after
  every append.
- **Subtasks:** 3 / 3 / 4 = 30 / 30 / 40 %, same shape as #3.
- **Measured:** reference slowest 67 ms, peak 13 MB of 256 MB; 66.9 KiB.

### 5. `hp_vec05_insert` — 1300, **TLE subtask**

- **Target:** `void insert(size_t pos, const T &value)`.
- **Grader stresses:** `10 k seed` appends up to 10⁶ elements with
  `insert(size(), x)` in one command — the amortized-growth test; front and
  scattered bulk inserts check the shifting; `pos > size()` must be a no-op;
  capacity is never printed.
- **slow.h:** one token different from the reference — `expand(mSize + 1)`
  instead of `ensureCapacity(mSize + 1)`, i.e. grow by exactly one slot.
  Correct, Θ(q²) for q appends. This is the classic mistake, and it is
  invisible below a few thousand elements.
- **Subtasks:** 5 / 5 = 50 / 50 % — ≤ 2 000 elements+inserts per block, then
  up to 10⁶ end-appends.
- **Measured:** reference slowest 146 ms, peak 27 MB of 256 MB; 25.7 KiB.
  `slow.h`: 16 ms on case 5, Time Limit Exceeded on case 6 (1002 ms), > 15×
  the limit on case 10. Score exactly 50 %.

### 6. `hp_vec06_erase_many` — 1600, **TLE subtask**

- **Target:** `void erase_many(const std::vector<size_t> &positions)`.
- **Grader stresses:** two position shapes, both built inside the grader — a
  dense contiguous run (`4 start 1 count`, up to 80 000) and a scattered
  ascending subset (`2 k seed`, up to 10⁵) — on up to 10⁶ elements; an empty
  list (no-op); lists that include index 0 and `size()-1`; rebuilds so every
  expensive call sees a full-size vector.
- **slow.h:** delete one position at a time, shifting the tail each time
  (with the `- i` offset the ascending order allows). Correct, Θ(k·n).
- **Subtasks:** 5 / 5 = 50 / 50 % — `n ≤ 2 000` and ≤ 2 000 deletions, then
  `n ≤ 10⁶` with up to 10⁵ positions per call.
- **Measured:** reference slowest 131 ms, peak 30 MB of 256 MB; 101.6 KiB.
  `slow.h`: 15 ms on case 5, TLE on case 6 (1004 ms), > 15× on case 10.

### 7. `hp_vec07_range_insert` — 1800, **TLE subtask**

- **Target:** `void range_insert(size_t pos, const std::vector<T> &values)`.
- **Grader stresses:** blocks of up to 2 × 10⁵ values built inside the grader
  and inserted at the front, in the middle, at `size()` (an append), past the
  end (no-op) and empty (no-op). Appending is the easy direction — nothing
  moves — so the deciding calls insert near the front of a large vector.
- **slow.h:** insert the block one element at a time, so the tail is shifted
  once per value. Correct, Θ(m·(n−pos)).
- **Subtasks:** 5 / 5 = 50 / 50 % — `n, m ≤ 600`, then `n` to 5 × 10⁵ with
  `m` to 2 × 10⁵.
- **Measured:** reference slowest 122 ms, peak 50 MB of 256 MB (the grader's
  own `std::vector` blocks plus a vector that grows past 10⁶ elements);
  42.0 KiB. `slow.h`: 9 ms on case 5, TLE on case 6 (1003 ms), > 15× on
  case 10.

### 8. `hp_vec08_block_swap` — 2000, **TLE subtask**

- **Target:** `void block_swap(size_t i, size_t j, size_t len)`.
- **Grader stresses:** `10 count seed maxlen` runs up to 20 000 *generated,
  always-valid, short* swaps on a million-element vector — the O(len)
  requirement; the explicit `2 i j len` commands carry every invalid shape
  (`len == 0`, `i == j`, overlapping ranges, a range running past the end,
  `len > size()`), all of which must leave the data untouched; `4` performs
  the largest legal swap (the two halves, `len = n/2`, which the catalogue
  asks for). The digest catches a swap that copies one block over the other.
- **slow.h:** snapshot the whole vector into a scratch array, then write the
  two blocks back from it. Correct, but Θ(n) time and Θ(n) extra memory per
  call.
- **Subtasks:** 5 / 5 = 50 / 50 % — `n ≤ 2 000` and ≤ 2 000 swaps, then `n` to
  10⁶ with up to 2 × 10⁴ short swaps.
- **Measured:** reference slowest 94 ms, peak 26 MB of 256 MB; 59.0 KiB.
  `slow.h`: 34 ms on case 5, TLE on case 6 (1007 ms), > 15× on case 10.

### 9. `hp_vec09_compress` — 2200, **TLE subtask**

- **Target:** `void compress()`; `push_back` pre-implemented.
- **Grader stresses:** `1 n seed runlen` builds up to 10⁶ elements in runs of a
  chosen average length, covering both extremes the catalogue asks for —
  `runlen = 1` (almost all distinct, nothing to remove) and `runlen = n` (all
  equal, everything but one element goes). The value space is deliberately
  tiny (7 ints / 9 long longs / 6 words), so *non-adjacent* equal values are
  everywhere: a solution that removes every duplicate value rather than every
  adjacent one fails immediately. `10` calls `compress()` twice and prints
  both results (idempotence); `resize` upwards creates a fresh run of `T()` to
  collapse; `push_back` builds a run at the end.
- **slow.h:** scan for an adjacent duplicate, erase it by shifting the tail,
  repeat. Correct, Θ(n) per removed element.
- **Subtasks:** 5 / 5 = 50 / 50 % — `n ≤ 2 000`, then `n` to 10⁶ mostly
  duplicates.
- **Measured:** reference slowest 169 ms, peak 56 MB of 256 MB (three blocks
  of up to 1.3 M elements, `long long` among them); 33.3 KiB. `slow.h`: 80 ms
  on case 5, TLE on case 6 (1006 ms), > 15× on case 10.

### 10. `hp_vec10_rotate` — 2500, **TLE subtask + 32 MB memory limit**

- **Target:** `void rotate(size_t k)`; `memory_limit_mb: 32`.
- **Grader stresses:** every `k` shape (0, 1, `size()-1`, `size()`,
  `size()+1`, multiples of `size()`, and up to 2·`size()` from a seed);
  `10 count seed` rotates repeatedly; `4` rotates by exactly `size()` (a
  no-op). The big block is 2 000 000 `long long` (16 MB) built with **one**
  `resize(n)` so the buffer is exactly n elements with no doubling slack, and
  it only ever shrinks afterwards. The copy-check command is used **only on
  the small blocks**: a second copy of a two-million-element vector would eat
  the budget the student needs.
- **slow.h:** rotate by one position, k times. Correct, Θ(k·n).
- **Subtasks:** 5 / 5 = 50 / 50 % — `n ≤ 1 500` (where both wrong approaches
  pass), then `n` to 2 × 10⁶ `long long`.
- **Measured:** reference slowest 153 ms of 1000 ms, peak 18 MB of 32 MB;
  63.5 KiB. `slow.h`: 71 ms on case 5, TLE on case 6 (1008 ms), > 15× on
  case 10.

**The memory half of this problem, measured separately.** `verify.py`'s
contract-3 check only accepts *Time Limit Exceeded* as the reason `slow.h`
stops (`failure_reason.startswith("Time Limit Exceeded")`), so the harness
cannot express "this solution must run out of memory". Rather than pretend, I
measured it by hand against the built bundle, inside the build image, with a
correct O(n)-time rotate that allocates a temporary copy of the data:

| address-space cap | reference | temp-buffer rotate |
|---|---|---|
| 32 MB (the problem's limit) | exit 0, output matches | `std::bad_alloc`, aborted |
| 40 MB | exit 0, output matches | `std::bad_alloc`, aborted |
| 48 MB | exit 0, output matches | exit 0, output matches |

on both case 6 and case 10. Peak RSS for the same two programs without a cap:
18 MB (reference) against 33.4 MB (temp buffer).

The cap is the right thing to measure, because the judge enforces memory as
**`RLIMIT_AS`** on the child, not as an RSS comparison:
`backend/scripts/time_wrapper.c` does
`set_limit(RLIMIT_AS, mem_mb * 1024 * 1024, "RLIMIT_AS")`. So the 32 MB limit
rejects a temp-buffer solution with ≥ 25 % to spare (it needs between 40 and
48 MB), while the reference fits with 14 MB of headroom on the stricter
virtual-memory measure. One honest consequence: the failure arrives as an
uncaught `std::bad_alloc` → `SIGABRT`, and the judge's evidence-based rule
(MLE only for SIGKILL with measured memory over the limit) will most likely
report that as **Runtime Error, not Memory Limit Exceeded**. The statement
therefore says the allocation fails and the program is terminated, instead of
promising a verdict name.

## Deviations from the catalogue

1. **Two extra complexity subtasks.** The catalogue marks only `erase_many`,
   `range_insert`, `compress` and `rotate` as complexity problems.
   `hp_vec05_insert` and `hp_vec08_block_swap` also got one, because each has
   a genuine, plausible, *correct* naive version in a worse complexity class
   (grow-by-one-slot; snapshot-the-whole-vector). Both are proven by
   `slow.h` scoring exactly 50 %.
2. **No complexity subtask for problems 1–4**, which have
   `"has_tle_subtask": false`. `fill`, bounds-checked `at`, `pop_front` and
   `erase` are Θ(n), Θ(1), Θ(n) and Θ(n−pos) in *every* implementation a
   student would plausibly submit; there is no honest naive version in a
   different complexity class. Their large subtasks buy scale and edge
   coverage instead. Each still ships a correct, genuinely slower `slow.h`
   with a comment saying exactly this, so the flag is the only thing that
   would need to change to promote them.
3. **Subtask shape.** Problems 1–4 use a three-tier 30/30/40 split (more
   informative for a correctness-only problem); the six complexity problems
   use 50/50, which is what the partial-credit promise requires given
   stop-on-first-failure scoring.
4. **`hp_vec03` / `hp_vec04` large-subtask bound.** Stated as a bound on the
   *total number of element moves* (~4 × 10⁷), not on the number of calls,
   since the operations are Θ(n) by design. `gen.py` carries that budget
   explicitly and sizes every bulk command against what is left of it.
5. **`std::vector` in two signatures.** `hp_vec06` and `hp_vec07` keep the
   catalogue's `const std::vector<…>&` parameters. `lib/vector.h` includes
   only `<iostream>` and `<stdexcept>`, and I may not edit it, so both
   `grader_main.cpp` and `starter_main.cpp` include `<vector>` **before**
   `"vector.h"`. Consequence worth knowing: a student who writes their own
   `main.cpp` must do the same (rule 5 forbids adding an `#include` to
   `student.h`). Both statements say so explicitly, and both main files carry
   a comment. The alternative — changing the signature to
   `const CP::vector<size_t>&` — would have avoided it but would have
   deviated from the catalogue's stated interface.
6. **Pre-implemented `push_back`.** Added through `meta.json`'s
   `declarations` as a complete inline definition (which the README allows) in
   `hp_vec03`, `hp_vec04` and `hp_vec09`, so the grader can interleave growth
   with the target function. It stays in the header, not in `student.h`.

## Open points

- `--measure` reports `slow.h` as "more than 15x the limit" on case 10 for all
  six complexity problems. That is the harness's measurement ceiling
  (`MEASURE_TIMEOUT_FACTOR = 15`), not the real factor; by construction the
  real factors are 10³–10⁶×, which is why case 6 already fails.
- The reference peaks at 50 MB (`hp_vec07`) and 56 MB (`hp_vec09`) of the
  256 MB limit. That is the *grader's* footprint (its own `std::vector` value
  blocks, and vectors that grow past 10⁶ elements), not the student's, and it
  leaves 4–5× headroom. If the production judge's box is tighter than this
  build image, those two are the ones to look at first.
- Every reference run sits at 6–17 % of its time limit on this machine, well
  inside `build.py`'s 50 % warning threshold, so no problem printed a timing
  warning.
- Total data for the ten problems: ~0.5 MB, far inside both the ~6 MB
  per-problem budget and the importer's 500 MB archive cap.
